# 04 · 压力测试：风险、被高估的点、止损条件

> 本文按“假设 → 挑战 → 验证 / 缓解”写。严重度：🔴 可能让项目失败　🟠 显著拖慢　🟡 需要留意。

## 先说结论：最可能出问题的三件事

1. 🔴 **售后数据的质量与“结果标签”**——你说“海量数据”，但数量不等于可用。
2. 🔴 **客户数据授权的商业谈判**——技术上能脱敏，不代表客户愿意回流。
3. 🔴 **建议的动作安全**——产线涉及高温、特气、高压，错误建议的代价是实物损失或人身安全。

## 可能被高估的点

- **“SLM 推理”**：小模型的多步推理和事实记忆有限。让它当调度员而非专家（见 README 决定 3）。
- **“Agent 看图分析”**：EL / 外观缺陷应由专用 CV 模型判断，SLM 只消费其结果。
- **“把论文喂进去就懂光伏”**：论文提供原理，不提供“你们设备上该怎么排查”。后者来自售后记录。
- **“集中式一定更强”**：集中的是脱敏知识；原始数据集中的收益小于合规与信任成本。
- **“设备厂商自己做 MES”**：客户通常已有 MES，你们做设备侧接口更稳妥。

## 逐项压力测试

### S1 🔴 售后数据质量
- **假设**：海量售后数据可直接转化为知识。
- **挑战**：常见问题——自由文本、格式混杂（工单 / Excel / 聊天）；只记了“怎么修”没记“为什么”；没记**修完是否真的解决**；同一症状不同工程师叫法不同；多个因素同时变更导致根因混淆。
- **验证**：P0-2 抽样 200 条，量化“四要素齐全率”“有结果标签比例”。
- **缓解**：先建 taxonomy；无结果标签的进待验证队列；对高频类别安排专家补标。

### S2 🔴 客户是否愿意回流
- **假设**：客户会共享 troubleshooting 数据。
- **挑战**：配方与良率是客户核心机密；贡献数据对客户没有直接回报；法务流程长。
- **验证**：P0-4 先看现有合同；P3 试点客户是否签 DUA。
- **缓解**：价值先行（本地 Agent 先帮客户解决问题）；设置激励（优先知识包、匿名对标）；L1 仅上传脱敏文本卡；**项目的成长不应依赖客户回流**——内部数据与转人工案例要能独立支撑 v1。

### S3 🔴 动作安全
- **假设**：Agent 的建议可被客户直接执行。
- **挑战**：错误的配方调整可能造成批量报废；特气 / 高压 / 高温场景有人身风险；客户可能把 Agent 输出当成权威。
- **缓解**：L0–L3 分级；L2 不给具体数值；L3 一律转人工；红队测试；每条建议带判定标准与回退方式；所有输出带置信度与免责边界；保留完整日志用于追责与复盘。

### S4 🟠 评测与基线缺失
- **挑战**：没有评测集就无法证明“变好了”，选型也只能凭感觉。
- **缓解**：P1-3 先建评测集（隔离于训练 / 检索库）；每次改动跑回归；同时测一个大模型作上限参照，帮助判断“差距来自模型还是来自知识”。

### S5 🟠 客户现场算力与运维
- **挑战**：已确认客户机房可放 GPU 服务器，但不同客户 GPU 型号不一；边缘节点的升级、监控、故障处理是持续成本；量化后模型的精度需实测。
- **验证**：P0 调研客户硬件；P1-7 在目标硬件上测延迟与精度。
- **缓解**：定义最小硬件规格并写入报价；提供托管选项；知识包与模型分开升级。

### S6 🟠 设备端周期长，容易拖累 Agent
- **挑战**：硬件改造、现场联调、认证周期长；老设备缺传感器。
- **缓解**：Agent v1 不依赖 FDC；Track A 先做信号清点和单变量 FDC，快速出可见价值；APC 先建议模式。

### S7 🟠 竞争与护城河
- **挑战**：客户可能已经在用通用大模型排障；SLM 本身没有壁垒，开源权重谁都能用。
- **判断**：真正的护城河是 ①**设备专属的案例与结果标签** ②**设备数据接入（FDC）** ③**与售后流程的闭环**。因此不要把资源过度投入模型本身。

### S8 🟡 知识漂移
- **挑战**：新机型、新浆料、新工艺会让旧结论失效。
- **缓解**：知识条目带适用范围与有效期；月度复审；评测集定期加入新案例。

### S9 🟡 多语言与术语
- **挑战**：客户与工程师可能中英文混用，设备与材料的缩写、别名多。
- **缓解**：taxonomy 中维护同义词表；评测集覆盖多语言场景。

### S10 🟡 数据合规与跨境
- **挑战**：客户跨国时，数据出境、保密、保留期各地要求不同。
- **缓解**：P0-4 梳理；本地优先、上行最小化；DUA 写清保留期与撤回；**请咨询法务**。

### S11 🟠 报警推送：风暴、疲劳、图纸版本、安全
- **挑战**：一个根因触发十几个报警，刷屏后客户会直接屏蔽推送；图纸版本与设备实际配置（改造后）不一致，会误导维修；图纸属于你们的 IP；报警涉及特气、超温时，错误建议代价极高。
- **缓解**：首发报警识别与合并；按严重度分级并跟踪“无用”反馈；设备台账（as-built）+ 权限水印链接；安全提示永远第一条，L3 动作一律转人工；LLM 不可用时仍推模板消息（确定性优先）。详见 `07`。

### S12 🔴 LLM 与数据安全
- **挑战**：LLM 推理是否会让知识库与客户数据暴露。
- **判断**：自托管下推理本身不对外传输；风险在 7 条数据流路径（云 API、进权重、跨客户、提示注入、日志、IP 外泄、供应链）。
- **缓解**：见 `06`——自托管、出站默认拒绝、客户数据不进权重、权限放检索层、收件人白名单、知识包签名。残余风险（提示注入无法彻底消除）需持续红队。

### S13 🟡 报警接入依赖客户配合
- **挑战**：客户可能不开放控制系统接口，或你们早期设备没有标准报警接口。
- **缓解**：先盘点接入方式（P0 待确认问题 4）；降级路径：日志监听、HMI 导出、邮件 / 短信转发；新机型把报警接口作为标配。

## 止损 / 转向条件

| 触发 | 动作 |
|---|---|
| P0-2 发现有“结果标签”的案例过少（如 <20%）且难以补标 | 暂停模型工作，先做 3 个月的数据治理与标注流程 |
| P2 评测始终低于指标且错误主因是“知识缺口” | 补案例 / 规则，而不是换更大的模型 |
| P2 评测始终低于指标且错误主因是“模型能力” | 换 / 升级模型，或收窄场景 |
| 红队测试反复出现越权建议 | 禁止发布；收紧输出模板（只给检查项，不给调整项） |
| P3 无客户愿意试点或续用 | 退回内部 copilot 形态，作为降本工具长期运行 |
| A3 在现场持续误报严重 | 暂停 A4 / A5，先修数据质量与阈值策略 |
| 报警推送上线后客户普遍屏蔽 / 忽略 | 暂停扩面，先做风暴抑制与分级，核查“无用”反馈 |

## 需要我进一步压测的方向

- 你们的设备具体品类 → 压测首发场景是否选对。
- 售后数据实际样例（脱敏）→ 压测 case card schema 是否够用。
- 客户合同条款 → 压测 L1 / L2 回流路径是否可行。
