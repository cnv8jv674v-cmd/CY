# 06 · LLM 与数据安全

## 0. 你的顾虑

> “如果还是用 LLM 推理，那么数据库的资料也不安全了。”

**LLM 本身不是泄露源，泄露发生在数据流经的地方。** 自托管的模型跑在你们或客户的机器上，推理过程不产生对外传输。真正的风险有 7 条路径，每条都有对应控制。

## 1. 七条泄露路径与控制

| # | 路径 | 控制 |
|---|---|---|
| 1 | **数据发给第三方云 LLM API** | 客户现场与内部知识库一律用**自托管开源权重模型**；Agent 节点**出站防火墙默认拒绝**，仅放行白名单（知识包更新源等）；外呼有审计 |
| 2 | **数据进入模型权重（训练）** | 客户数据**不进权重**，只进可删除的检索库；微调仅使用内部数据或已审核的脱敏卡；客户撤回授权时，从检索库删除即可 |
| 3 | **跨客户泄露（多租户）** | 每个客户独立的边缘节点与索引；中心下发的知识包只含脱敏、审核过的内容；增加“跨客户泄露”红队用例 |
| 4 | **提示注入与外泄**（上传的日志、文件、图片里藏指令） | 上传内容一律当**数据**而不是指令；Agent 无外网、工具权限最小化；**推送收件人白名单**，Agent 不能向未登记地址发送文件；输出过滤 |
| 5 | **会话与日志留存** | 加密存储、明确保留期、客户可删除、访问审计；日志里的人员信息最小化（欧洲客户涉及 GDPR 等个人数据规则，需法务确认） |
| 6 | **你们自己的 IP 外泄（图纸、售后库、know-how）** | 知识分级（见下）；图纸走带权限、带水印、带有效期的链接，而不是随手附件；下发知识包前过滤为“客户可见”级 |
| 7 | **供应链**（模型权重、依赖、知识包被篡改） | 权重与依赖校验来源与哈希；知识包签名，节点只接受签名包；支持回滚 |

### 一条关键原则

**权限控制放在检索层，而不是写在提示词里。** 提示词里写“不要泄露其他客户的数据”约束不了模型；应在检索时就过滤掉用户无权看到的内容，让模型根本看不到。

## 2. 数据分级与可用处理环境

| 级别 | 例子 | 可用的处理环境 |
|---|---|---|
| D0 公开 | 公开论文、公开手册 | 任意 |
| D1 厂商内部 | 售后库、图纸、know-how | **自托管**；若考虑外部 API，仅限已签订企业数据条款的服务，且由你们决策 |
| D2 客户机密 | 配方、良率绝对值、原始 trace、会话 | **仅客户现场**，本地模型 |
| D3 个人数据 | 人员姓名、账号 | 最小化或去除；按地区法规处理 |

> 自托管模型通常弱于前沿云端模型。弥补方式是：检索 + 规则 + 受限生成，而不是把更多数据送出去。对于只涉及 D0、或已充分脱敏的 D1 任务（例如起草 playbook 草稿），**是否使用外部服务**是一个有取舍的商业决策，需结合合同再定。

## 4. 残余风险（诚实地说）

- **提示注入无法被彻底消除**，只能降低影响：靠最小权限、无外网、白名单收件人。
- **自托管模型的维护成本**：补丁、权重更新、监控由你们承担。
- **脱敏不是绝对的**：极罕见的工况组合可能被反推客户，见 `02` 的泛化规则。
- 合同与法务比技术手段更关键，**请咨询法务**，我不是律师。
