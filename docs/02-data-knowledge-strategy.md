# 02 · 数据与知识策略

## 1. 你的约束：本地 vs 中心化

**结论：你的直觉对一半。** 要成长，确实需要中心化；但需要中心化的是**知识**，不是**客户原始数据**。

### 四条数据流

| 流向 | 内容 | 条件 |
|---|---|---|
| ↓ 下行 | 知识包、规则树、模型 / LoRA 适配器、CV 模型 | 无隐私问题；签名、版本化、可回滚 |
| ↑ 上行 L1 | **脱敏 case card**（结构化文本，无图，参数归一化） | 合同授权 + 每单客户确认 |
| ↑ 上行 L2 | 原始图片 / 参数 / 日志 | **仅转人工时**，与现有售后流程同权限，单次授权、限期 |
| ✕ 不上行 | 配方原值、产能 / 良率绝对值、客户身份、原始 trace | 默认不出厂 |

### 几点说明

- **客户侧永远不需要你的全量数据库**，只需要“当前适用的知识包”。你的售后库留在中心；下发的是它蒸馏后的版本。
- **联邦学习**理论可行，但在“SLM + 小样本 + 异构设备”下工程复杂、收益不明。建议 P4 再评估，不作为 v1 路径。
- **无法保证所有客户都愿意回流。** 因此飞轮的第一来源必须是你们**内部售后数据**与**转人工案例**（客户本来就在向你们提供数据），而不是指望客户自愿贡献。
- 对愿意用云的客户，可提供“托管版”作为选项，但不要把它作为默认。

### 脱敏规则（v0.1）

| 对象 | 规则 |
|---|---|
| 身份信息 | 客户名、厂名、线号、人员、批次号 → 删除或哈希 / 类别化 |
| 参数 | 用**相对偏差 / 百分位**表示（如“管温较设定 +8 ℃”），不上传配方绝对值 |
| 绝对业绩 | 良率、产能、效率绝对值 → 分档（如“良率下降 1–2 个百分点”） |
| 图片 | 默认不上传；上传时去 EXIF、水印、铭牌、批次码 |
| 自由文本 | NER 过滤 + 人工抽检 |
| 再识别风险 | 极罕见的“设备 + 工况 + 时间”组合 → 泛化（k-匿名思想），必要时不入库 |

> 合同和授权比技术脱敏更重要：需要一份**数据使用补充协议（DUA）**，写清上行内容、用途、保留期、撤回方式。具体条款请咨询法务，我不是律师。

## 2. 技术数据怎么“喂”

**不是把论文和售后记录一股脑扔进中心服务器。** 三类知识，用法完全不同：

| 类 | 例子 | 处理 | 进哪里 |
|---|---|---|---|
| **A 案例知识（核心）** | 售后工单、排查记录、维修报告 | 清洗 → case card → 专家审核 | 检索库（主）+ 评测集 + 少量微调数据 |
| **B 结构化专家知识** | 工艺流程与参数关系、设备手册、报警码表、SOP、FMEA | 结构化成规则树 / 表格 / 知识图谱 | 规则树 + RAG |
| **C 外部文献** | 论文、行业标准、材料 TDS | 选择性摄取，摘要 + 出处；**注意版权许可** | RAG（背景 / 解释），不训练 |

### SLM 微调只学三件事

1. **对话协议**：学会追问、学会何时转人工。
2. **输出格式**：1.2.3.4 步骤 + 判定标准 + 风险提示。
3. **术语与工具调用**：光伏术语、何时调用哪个工具。

**事实性内容通过检索获得，不烧进权重**，原因：可更新、可溯源、可删除（客户撤回授权时）。进了权重的数据无法撤回。

### A 类数据处理流水线

1. **盘点与摄取**：数据源（已确认为 Excel / PDF / 文字）、数量、语言、覆盖机型。摄取按格式处理：
   - **Excel**：多 sheet、合并单元格、列名不统一 → 先做列映射表，统一为长表；保留来源文件与行号。
   - **PDF**：先判断**文字版还是扫描件**；扫描件需 OCR（中英文及客户本地语言），表格单独处理；保留页码。
   - **文字**（工单、邮件、聊天记录）：先切分为“事件”，去除签名、转发链、重复引用；保留时间戳与发送方角色。
   - 每条记录保留**来源引用**（文件、页 / 行），case card 可回溯到原始记录。
   - **含客户信息的原始文件只在自托管环境处理**（见 `06`）。
2. **抽样质检**：随机 200 条，检查是否具备“现象 / 原因 / 措施 / 结果”四要素。
3. **Taxonomy workshop**：与 3–5 位资深售后 / 工艺专家定统一分类（症状、工序段、根因类别）。**这一步决定后面所有事，必须放最前。**
4. **LLM 辅助抽取**：生成 case card 草稿。售后数据含客户信息，须在你们自己控制的环境里处理。
5. **专家审核**：高频类别全审，长尾抽检。
6. **标注结果**：已解决 / 部分 / 未解决 / 未知。**无结果标签的卡进“待验证队列”，不进主库。**
7. **去重与合并**，版本化。
8. **切分**：检索库 / 评测集（留出约 15–20%，按时间或机型切，**不得进训练**）/ 微调集。

Case card 结构见 `schemas/case_card.schema.json`。

## 3. 成长飞轮

```
内部售后数据 ─┐
转人工案例 ───┼→ case card（审核）→ 知识包 → 下发客户 → 更多会话与结果标签 ─┐
客户授权回流 ─┘                                                        │
        ↑──────────────────────────────────────────────────────────────┘
```

- **阶段 1（内部 copilot）**：100% 数据可用，同步建立评测集与反馈信号（采纳 / 修改 / 忽略）。
- **阶段 2（客户试点）**：每次结案让客户选择是否贡献匿名案例。
- **激励**：贡献方优先获得新知识包、匿名行业对标、更快响应。
- **质量**：只有带结果标签且经审核的案例进入主库。
- **漂移管理**：知识包条目带**适用范围与有效期**（新机型 / 新浆料 / 新工艺会让旧结论过期）。
