# 07 · EAP 说明与“报警驱动推送”设计

## 1. EAP 是什么

**EAP = Equipment Automation Program（设备自动化程序）。** 它是一层运行在设备侧（或设备与工厂系统之间）的软件，把一台设备变成工厂系统可以**读取、也可以受控**的标准节点。

在半导体行业，EAP 位于 MES 与设备之间，通常通过 SECS/GEM（SEMI E5 / E30）通信。光伏行业的设备接口标准化程度较低，常见的是 OPC UA、Modbus、厂商私有协议，所以**接口方式要以你们设备和客户实际情况确定**。

### 四类功能

| 功能 | 做什么 |
|---|---|
| 数据采集 | 设备状态、报警、工艺参数、事件（开始 / 结束 / 配方切换 / 维护） |
| 配方管理 | 配方下发、校验、版本管理、防呆（防止错配方） |
| 远程控制 | 启停、暂停（hold）、调度；**权限与风险高，默认关闭或需审批** |
| 与 MES 交互 | 上报载具 / 批次的进出、状态机、追溯数据 |

### 在整体架构里的位置

```
设备 PLC / 控制系统 ⇄ EAP ⇄ ┬ 客户 MES（工单、追溯、排产）
                            ├ Agent 边缘节点（报警、对话排障）
                            ├ FDC（故障检测）
                            └ APC（过程控制）
```

### EAP 与 MES 的区别

| | MES | EAP |
|---|---|---|
| 层级 | 工厂 / 产线级 | 设备级 |
| 管什么 | 工单、物料、排产、追溯 | 设备怎么被自动化、数据怎么出来、配方怎么下去 |
| 谁拥有 | 客户（常自建或已采购） | 设备厂商最有优势 |

### 回到我之前那一段（L4）说的“定位”，具体是

> “定位为设备侧接口 + 追溯字段，与客户现有 MES 对接，不要替代它。”

具体指你们交付三样东西，而不是去卖一套 MES：

1. **设备端 EAP / 标准接口包**：把你们设备的报警、状态、参数、配方暴露出来。
2. **追溯字段**：载具 / 舟号 / 管号、工艺开始与结束时间、配方名与版本、报警记录。
3. **与客户 MES 的适配**：按客户 MES 的接口规范做对接。

原因：客户通常已有 MES（有的是自研），替换它的政治与成本太高；而你们的优势在于**设备级数据的丰富度**，这也是 Agent 和 FDC 最需要的。

### 你们的干法设备上，EAP 通常关心什么（示例，以实际设备为准）

管式炉类（LPCVD、boron / POCl3 diffusion、oxidation）按**批次 / 载具**工作，常见数据：多温区温度曲线、压力、各气路流量、工艺时间、推舟与舟位、泄漏检测、水冷与排风状态、报警。laser opening 则是片级工艺，关注激光功率、扫描与对位等。

## 2. 报警驱动推送：设计

### 你的需求

> 例如 boron diffusion 某个报警出现，Agent 推送：设备号、报警信息、建议维修方案给客户的设备部门。
>
> **v0.4 修改：Agent 不向客户发送图纸。** 只给文字维修方案；如果客户能拍照反馈，Agent 分析照片并指出图中哪个零部件可能需要更换（见第 9 节）。图纸只在你们内部使用。

### 流程

```
设备报警 → EAP / 采集网关 → 去重与风暴抑制 → 匹配 Alarm Playbook（机型 + 报警码 + 当前状态）
  → LLM 组织成面向设备部门的消息（不改变事实内容）→ 推送（邮件 / 企业 IM / 工单）
  → 设备部门按步骤检查；可选：拍照反馈 → 照片分析 → 指出可疑零部件
  → 设备部门反馈（有用 / 无用 / 已解决 + 实际根因 + 实际更换的零件）→ 结案 → case card
```

全程在**客户本地网络内**完成，不出厂。是否同时给你们售后开工单，由客户**选择**（默认不开）。

### 推送消息内容

| 字段 | 说明 |
|---|---|
| 设备号 / 机型 / 工序 | 例如“设备 #xx，boron diffusion” |
| 报警码与文本、发生时间 | 来自设备 |
| 当前批次 / 配方（如有） | 来自 EAP |
| 严重度 | info / warning / high / critical |
| **安全提示（始终第一条）** | 先按现场 SOP 确认设备安全状态；涉及特气、高温、高压的操作由授权人员执行 |
| 可能原因（按概率排序） | 来自 playbook |
| 排查步骤 | 含判定标准与风险等级 |
| 所需备件 | 件号与名称 |
| 零部件位置说明 | **文字描述**（部件名称、件号、位置、外观特征），**不附图纸** |
| 拍照反馈入口 | 拍摄指引 + 上传方式，可选 |
| 升级条件 | 何时联系厂商 |
| 历史相似案例（可选） | 摘要 |

### Alarm Playbook 条目示例（占位，非真实设备数据）


## 3. 关键设计点

1. **确定性优先。** 报警 → playbook 匹配 → 推送，走确定性路径；LLM 只负责措辞与组织。**LLM 不可用时，仍推送模板化消息**，保证不漏报。
2. **报警风暴与级联。** 一个根因常触发多个报警：识别首发报警，合并相关报警，避免刷屏。
3. **防推送疲劳。** 按严重度分级，只推送可操作的内容；客户可配置；跟踪“无用”反馈。
4. **设备台账（as-built）。** 虽然图纸不发给客户，建议的零部件仍必须与**该台设备的实际配置**对应（改造后可能偏离出厂版本），否则会推荐错件号。台账 + 内部图纸用来生成面向客户的“件号 + 位置文字描述”。出口管制与技术资料合规请法务确认。
5. **安全红线。** 报警涉及特气泄漏、超温、火灾相关时，第一条永远是进入安全状态 / 联系安全员；任何绕过互锁的建议一律禁止（L3）。
6. **收件人白名单。** 只能推送给已登记的设备部门联系人，Agent 不能向其他地址发送文件。
7. **反馈闭环。** 每条推送带“有用 / 无用 / 已解决 + 实际根因”，这是结果标签的最佳来源。
8. **多语言与跨时区。** 客户在东南亚 / 欧洲 / 美国：消息至少支持中英文及客户本地常用语言；转人工要考虑跨时区排班。

## 4. 对 Track A 的影响

报警推送需要**读到设备报警**，所以设备端的**报警通道（alarm-only）要在 A1–A2 提前做**，不必等 FDC 与 APC。最小需求：**设备号 + 报警码 + 时间 + 当前配方 / 批次 / 管号**。

客户不开放 EAP 接口时的降级方案：监听报警日志文件（CSV / 文本）、HMI 报警导出、邮件或短信转发。

## 5. PLC 接入（已确认设备控制为 PLC）

**原则：只读、网络隔离、不影响控制。**

接入路径（按优先级，取决于 PLC 品牌与是否有上位机）：

1. PLC 自带的 OPC UA 服务器（若型号支持）。
2. 上位机 / SCADA 提供的 OPC UA、数据库或报警日志。
3. Modbus TCP 或厂商私有协议。
4. 报警日志文件监听（降级）。

做法：

- 采集网关位于设备网络与客户 IT 网络之间，使用**只读账号**；OT / IT 网络分段，网关出向只允许到 Agent 节点。
- **报警映射表**（PLC 报警位 / 报警号 → 报警码、文本、严重度）是关键资产，要进数据字典。报警文本常在上位机 / HMI 里，需要软件工程师提供。
- 采集不能拖慢控制：用订阅或批量读取、降低轮询频率，上线前测对扫描周期的影响。
- 不开放写入。若以后 APC 要写参数（A5），单独评审。
- PLC 品牌 / 型号待确认，会决定具体协议与工作量。

## 6. 推送渠道：邮件与 WhatsApp

**结论：邮件做主通道；WhatsApp 可行，但只作“提醒指针”，不承载详细内容与照片。**

原因：

1. WhatsApp 商业消息要求用户**明确 opt-in**；主动发起的消息必须使用**预先审批的模板**；号码质量评分过低会被限制甚至封号（来源：WhatsApp 服务商 360dialog 的最佳实践文档）。模板是固定格式、少量变量，与“确定性优先”相容，但 LLM 自由措辞的空间会被压缩。会话窗口等具体规则以 Meta 当前文档为准，我没有逐条核实。
2. 消息会经过 Meta 及（如使用）服务商的系统，偏离“客户数据不出厂”。设备号和报警码不如配方敏感，但仍属客户信息，以 Meta 当前条款与合同为准。
3. 设备照片和详细维修内容也不建议经 WhatsApp：照片可能带出 HMI 屏幕上的配方等客户机密。
4. 客户 IT 可能限制；个人手机号属个人数据（欧洲客户涉及 GDPR 等规则）。
5. 地区习惯：东南亚使用广泛；欧美客户可能更习惯邮件、Teams 或 Slack。这是一般性判断，需向客户确认。

推荐分层：

| 通道 | 用途 | 内容 |
|---|---|---|
| 邮件（主） | 完整报警包 | 设备号、报警、可能原因、排查步骤、备件（件号 + 位置文字描述）、拍照上传入口 |
| WhatsApp（可选，客户 opt-in） | 严重报警提醒 + 快捷反馈 | 一行：严重度 / 设备号 / 报警码 + “详情见邮件”；快捷回复：已收到 / 已处理 / 无用 |
| 企业 IM / 工单（后续） | Teams / Slack / 工单系统适配 | 与客户习惯对齐 |

实现要点：

- **通道适配器**抽象：邮件先行，WhatsApp 作为 P3 可选；每个客户可配置通道与收件人。
- **邮件使用客户自己的 SMTP / 邮箱**，发到客户内部地址，数据不出客户环境；若从你们的域发出，则数据已经出厂，需要客户同意。
- 收件人白名单；收到的回复一律按**不可信输入**处理（提示注入）；反馈用结构化按钮，不用自由文本。
- 能否推到 WhatsApp 群组、是否支持，需查 Meta 当前文档确认，我没有核实。

## 7. 图纸（PDF，已有版本管理）：仅内部使用

**v0.4：图纸不发给客户，也不放到客户节点。** 图纸的作用是你们内部用的“原料”：

1. 建立 **报警 → 部件 → 件号 → 位置描述** 的映射，生成面向客户的文字说明（Alarm Playbook 里的 `parts_detail`）。
2. 生成**零部件参考包**（件号、名称、位置描述、外观特征、参考照片），用于照片分析（第 9 节）。参考包**不含工程图**。
3. 需要已有的版本管理：索引按（图号，版本）建，并与设备序列号的 as-built 台账对应。
4. PDF 若为扫描件需 OCR。图纸文件本体不进向量库，只入元数据与页级文本索引，且只存在于你们的内部环境。

## 9. 拍照反馈与零部件识别

### 流程

```
推送（含拍摄指引）→ 设备部门拍照并回传 → 隐私处理（去 EXIF、HMI 屏幕检测）
  → 照片分析（视觉模型 + 零部件参考包 + 当前报警上下文）
  → 在客户自己的照片上标注可疑零部件 + 文字：名称 / 件号 / 位置 / 观察到的现象 / 置信度
  → 验证步骤 → 工程师确认后再更换 → 反馈实际更换的零件
```

### 输出规则

- 标注画在**客户自己拍的照片**上，不引入图纸内容。
- 只说“**可疑零部件**”，并给出**依据**（例如“O 型圈有压痕变形”）和**置信度**，不直接下“必须更换”。
- 达到证据标准（明显的开裂、烧蚀、变形、腐蚀、积垢等）才建议更换；否则建议“需进一步检查”，并给出下一步拍什么。
- 置信度低 → 请求补拍（指明角度、距离、需要包含的铭牌）或转人工。
- 更换前要核对件号；高风险部件（涉及气体、高温、高压）只提示由授权人员处理（L2/L3）。
- 照片里文字（铭牌、屏幕、便签）按**数据**处理，不当作指令。

### 数据与方案

| 需要 | 说明 |
|---|---|
| 零部件参考包 | 目标设备的关键部件：件号、名称、位置描述、外观特征、多角度参考照片 |
| 带标签的故障照片 | 历史售后里的失效件照片（变形的 O 型圈、烧蚀的加热件等），与实际更换结论对应；**有多少这类照片，决定能做到多准** |
| 视觉模型 | 通用多模态模型 + 专用检测 / 分类模型的组合；以留出集实测选型 |

### 一个需要你决定的架构问题

照片分析需要“参考资料”。因为图纸不下发到客户，有三种做法：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| A（默认建议） | 客户节点只存**零部件参考包**（不含工程图），本地分析 | 照片不出厂 | 参考包仍是你们的部分 IP，要做访问控制与加密 |
| B | 照片经客户同意后传到你们环境分析 | 参考资料全在内部 | 客户照片出厂，需合同与授权；跨境合规 |
| C | 低置信度或敏感场景转人工看图 | 最稳 | 占用人力 |

建议 **A 为主，C 兜底**；B 仅用于客户明确同意的场景。

### 照片隐私与质量

- 照片可能拍到 **HMI 屏幕（配方参数）、人员、其他设备布局**：拍摄指引里提醒避开；自动检测屏幕区域并遮挡；去 EXIF；限定保留期；仅客户现场存储。
- 现场光线差、炉内难拍：给拍摄指引（角度、距离、补光、带参照物、拍铭牌）。
- 通道：邮件回传或安全上传链接；不建议用 WhatsApp 传设备照片。
