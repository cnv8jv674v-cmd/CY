# 07 · EAP 说明与“报警驱动推送”设计

## 1. EAP 是什么

**EAP = Equipment Automation Program（设备自动化程序）。** 它是一层运行在设备侧（或设备与工厂系统之间）的软件，把一台设备变成工厂系统可以**读取、也可以受控**的标准节点。

在半导体行业，EAP 位于 MES 与设备之间，通常通过 SECS/GEM（SEMI E5 / E30）通信。光伏行业的设备接口标准化程度较低，常见的是 OPC UA、Modbus、厂商私有协议，所以**接口方式要以你们设备和客户实际情况确定**。

### 四类功能

| 功能 | 做什么 |
|---|---|
| 数据采集 | 设备状态、报警、工艺参数、事件（开始 / 结束 / 配方切换 / 维护） |
| 配方管理 | 配方下发、校验、版本管理、防呆（防止错配方） |
| 远程控制 | 启停、暂停（hold）、调度；**权限与风险高，默认关闭或需审批** |
| 与 MES 交互 | 上报载具 / 批次的进出、状态机、追溯数据 |

### 在整体架构里的位置

```
设备 PLC / 控制系统 ⇄ EAP ⇄ ┬ 客户 MES（工单、追溯、排产）
                            ├ Agent 边缘节点（报警、对话排障）
                            ├ FDC（故障检测）
                            └ APC（过程控制）
```

### EAP 与 MES 的区别

| | MES | EAP |
|---|---|---|
| 层级 | 工厂 / 产线级 | 设备级 |
| 管什么 | 工单、物料、排产、追溯 | 设备怎么被自动化、数据怎么出来、配方怎么下去 |
| 谁拥有 | 客户（常自建或已采购） | 设备厂商最有优势 |

### 回到我之前那一段（L4）说的“定位”，具体是

> “定位为设备侧接口 + 追溯字段，与客户现有 MES 对接，不要替代它。”

具体指你们交付三样东西，而不是去卖一套 MES：

1. **设备端 EAP / 标准接口包**：把你们设备的报警、状态、参数、配方暴露出来。
2. **追溯字段**：载具 / 舟号 / 管号、工艺开始与结束时间、配方名与版本、报警记录。
3. **与客户 MES 的适配**：按客户 MES 的接口规范做对接。

原因：客户通常已有 MES（有的是自研），替换它的政治与成本太高；而你们的优势在于**设备级数据的丰富度**，这也是 Agent 和 FDC 最需要的。

### 你们的干法设备上，EAP 通常关心什么（示例，以实际设备为准）

管式炉类（LPCVD、boron / POCl3 diffusion、oxidation）按**批次 / 载具**工作，常见数据：多温区温度曲线、压力、各气路流量、工艺时间、推舟与舟位、泄漏检测、水冷与排风状态、报警。laser opening 则是片级工艺，关注激光功率、扫描与对位等。

## 2. 报警驱动推送：设计

### 你的需求

> 例如 boron diffusion 某个报警出现，Agent 推送：设备号、报警信息、建议维修方案、图纸给客户的设备部门。

### 流程

```
设备报警 → EAP / 采集网关 → 去重与风暴抑制 → 匹配 Alarm Playbook（机型 + 报警码 + 当前状态）
  → LLM 组织成面向设备部门的消息（不改变事实内容）→ 推送（邮件 / 企业 IM / 工单）
  → 设备部门反馈（有用 / 无用 / 已解决 + 实际根因）→ 结案 → case card
```

全程在**客户本地网络内**完成，不出厂。是否同时给你们售后开工单，由客户**选择**（默认不开）。

### 推送消息内容

| 字段 | 说明 |
|---|---|
| 设备号 / 机型 / 工序 | 例如“设备 #xx，boron diffusion” |
| 报警码与文本、发生时间 | 来自设备 |
| 当前批次 / 配方（如有） | 来自 EAP |
| 严重度 | info / warning / high / critical |
| **安全提示（始终第一条）** | 先按现场 SOP 确认设备安全状态；涉及特气、高温、高压的操作由授权人员执行 |
| 可能原因（按概率排序） | 来自 playbook |
| 排查步骤 | 含判定标准与风险等级 |
| 所需备件 | 件号与名称 |
| 图纸 / 手册 | 图号、版本、章节，**权限链接**而非附件 |
| 升级条件 | 何时联系厂商 |
| 历史相似案例（可选） | 摘要 |

## 3. 关键设计点

1. **确定性优先。** 报警 → playbook 匹配 → 推送，走确定性路径；LLM 只负责措辞与组织。**LLM 不可用时，仍推送模板化消息**，保证不漏报。
2. **报警风暴与级联。** 一个根因常触发多个报警：识别首发报警，合并相关报警，避免刷屏。
3. **防推送疲劳。** 按严重度分级，只推送可操作的内容；客户可配置；跟踪“无用”反馈。
4. **图纸版本与设备台账。** 图纸必须与**该台设备的实际配置**对应（改造后可能偏离出厂版本），所以要有 as-built 台账。图纸属于你们的 IP：水印、权限链接、有效期。出口管制与技术资料合规请法务确认。
5. **安全红线。** 报警涉及特气泄漏、超温、火灾相关时，第一条永远是进入安全状态 / 联系安全员；任何绕过互锁的建议一律禁止（L3）。
6. **收件人白名单。** 只能推送给已登记的设备部门联系人，Agent 不能向其他地址发送文件。
7. **反馈闭环。** 每条推送带“有用 / 无用 / 已解决 + 实际根因”，这是结果标签的最佳来源。
8. **多语言与跨时区。** 客户在东南亚 / 欧洲 / 美国：消息至少支持中英文及客户本地常用语言；转人工要考虑跨时区排班。

## 4. 对 Track A 的影响

报警推送需要**读到设备报警**，所以设备端的**报警通道（alarm-only）要在 A1–A2 提前做**，不必等 FDC 与 APC。最小需求：**设备号 + 报警码 + 时间 + 当前配方 / 批次 / 管号**。

客户不开放 EAP 接口时的降级方案：监听报警日志文件（CSV / 文本）、HMI 报警导出、邮件或短信转发。
