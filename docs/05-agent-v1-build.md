# 05 · Agent V1 如何生成

## 0. 先定义 V1

V1 不是“什么都能聊的光伏大模型”，而是**一个垂直切片**：

- **范围**：先做 1 类设备。建议 **boron diffusion** 先行（你举过报警推送的例子，场景清晰），最终以“工单 / 报警频次最高”为准。跑通后复制到另外四类：LPCVD、POCl3 diffusion、oxidation、laser opening。
- **两个入口**
  - **A 报警驱动**：设备报警 → 推送设备号、报警信息、维修建议、图纸给客户设备部门（详见 `07`）。
  - **B 对话排障**：客户描述问题（良率 / 效率 / 缺陷）→ Agent 引导补充数据 → 排查步骤 → 转人工（详见 `01`）。
- **用户**：先是你们自己的售后工程师（内部 copilot），验证后才进客户现场。
- **全线工艺 know-how**（湿法、金属化等）在 V1 中作为**因果知识**使用（例如“效率下降可能来自上游哪些工序”），**不单独做这些工序的设备对话**，避免范围失控。

> 我的判断：**报警驱动（A）比对话排障（B）更适合当 V1 主打。** 报警码是确定的、有限的，可以做成高精度手册；对话排障的输入开放得多，难度高得多。A 先跑通并积累结果标签，再扩 B。

## 1. V1 由哪些部分“生成”

| 组件 | 怎么生成 | 主要来源 | 谁做 |
|---|---|---|---|
| **报警手册（Alarm Playbook）** | LLM 辅助起草 → 专家逐条审核 → 版本化入库 | 设备手册、售后工单、工程师访谈 | 售后 / 设备专家 + 数据工程 |
| **Case card 库** | 见 `02` 的 8 步流水线 | 售后记录 | 数据工程 + 专家抽检 |
| **工艺因果表** | 访谈整理：症状 ↔ 工序 ↔ 设备状态 | 工艺工程师（覆盖全线） | 工艺专家 |
| **图纸 / 手册索引** | 只建**元数据索引**（图号、版本、适用机型、部件、关联件号），文件本体不进向量库 | 图纸库、手册 | 文档管理 + 数据工程 |
| **编排 + LLM** | 自托管开源权重模型 + 显式状态机 + 检索 + 工具 | — | 软件 / ML |
| **评测集** | 用历史工单做**回放**（见下） | 历史工单 | 数据 + 专家 |

### LLM 在 V1 里只做三件事

1. **提问**：按信息增益追问缺失信息。
2. **组织**：把检索到的 playbook / case card 内容整理成人能读的步骤。
3. **格式化**：套用输出模板（步骤 + 判定标准 + 风险等级 + 置信度）。

**事实内容必须来自 playbook / case card，并引用来源 ID。** 检索不到来源时，Agent 回答“知识库没有该项”并转人工，而不是凭记忆编。

## 2. 逐步生成（对应路线图）

| 步骤 | 阶段 | 内容 |
|---|---|---|
| 1 | P0 | 选定切片；拉三张清单：去重后的报警码清单、近 12 个月该设备工单 Top 20 症状、现有手册 / 图纸清单 |
| 2 | P0–P1 | 定 taxonomy；定 playbook 与 case card schema |
| 3 | P1 | 生成 **Alarm Playbook v0**：按频次 × 严重度排序，先覆盖历史报警量的大部分（目标值待数据盘点后定） |
| 4 | P1 | 抽取 case card（含结果标签） |
| 5 | P1 | 图纸 / 手册索引库 + **设备台账**（每台设备实际配置与图纸版本的对应） |
| 6 | P1 | 检索：**报警码走精确索引**（机型 + 码），症状走混合检索 |
| 7 | P1 | 评测集：历史工单回放。输入（机型、报警、现象描述）→ 期望（根因类别、关键排查步骤）；留出集不进检索库 |
| 8 | P2 | 编排 + 生成：状态机驱动，LLM 受限于检索内容 |
| 9 | P2 | 报警推送链路（`07`） |
| 10 | P2 | 内部灰度：工程师采纳 / 修改 / 忽略 → 反馈变成新 case card → 周度评测迭代 |

## 3. 技术栈（建议，非定论）

- **推理**：自托管（vLLM 或 llama.cpp 类服务），开源权重模型。客户机房可放 GPU，因此**不必局限在极小模型**；“SLM”的价值是可控、成本、可私有化，具体规模由 P1-7 评测确定——选“够用的最小”。
- **检索**：PostgreSQL + pgvector 或 Qdrant 等 + BM25 关键词；报警码用精确索引。
- **编排**：显式状态机（自写或 LangGraph 类框架），不让 LLM 自由规划流程。
- **视觉**：专用 CV 分类模型处理 EL / 外观缺陷。
- **前端与推送**：Web 对话 + 邮件 / 企业 IM / 工单系统（按客户习惯）。
- **知识版本**：playbook 用 YAML 或 JSON 文件，走 git 式评审与版本管理。

## 4. 你需要准备的东西

1. 该设备类型的**报警清单**（码、文本、级别）。
2. 近 12–24 个月该设备的**工单**：先给 20–30 条**脱敏样本**，我据此验证 schema。
3. 设备**手册 / 维保手册 / 图纸清单**（图号、版本、适用机型）。
4. **备件清单与件号体系**。
5. 2–3 位专家，**每周约 2 小时**审核 playbook 与 case card。

> 样本请先脱敏，不要在对话里贴客户机密、配方原值或受控图纸（见 `06`）。

## 5. V1 完成标准（DoD）

- 目标设备类型的 playbook 覆盖历史报警量的约定比例，且 100% 条目经专家审核。
- 评测集上 Top-3 命中率与“应转人工”识别率达到 P0-5 指标。
- 红队测试零越权（L2/L3 动作无具体数值与操作指引）。
- 内部灰度 ≥4 周，工程师采纳率有记录且趋势向好。
- **LLM 不可用时，报警推送仍能以模板化消息送达**（见 `07` 的确定性优先原则）。
